# Reference Geometry Import

Reference geometry import is intentionally separate from the steel BIM project model.

## Boundary

External source formats such as DXF, DWG, STEP, IFC, and E57 are translated outside the core project model into a canonical `bobercad-reference-geometry` JSON file. The viewer reads that file as a read-only overlay.

Project JSON may store only:

- reference asset path
- visibility and display overrides
- transform into the project coordinate system
- future snap/import policy flags

Project JSON must not store translated meshes, vertices, faces, B-reps, point-cloud payloads, or generated CAD scene data.

Direct scene construction mirrors this pointer boundary when tests or runtime code pass ready `referenceGeometryAssets` directly to `buildScene`: project asset path, fields, flags, display keys, behavioral display controls, and transform shape are checked before preview stats or primitives are emitted. Malformed project display color/opacity override values still fall back to viewer defaults or the next valid display source rather than leaking into primitives, while malformed `visible` and `pointSize` controls reject the direct pointer envelope. Point-cloud `pointAttributes` must be canonical records with known attribute keys before direct runtime data is accepted. Preloaded point-cloud chunk sidecars are also treated as canonical records; malformed sidecar envelopes, unsafe or mismatched wrapper ids, missing schema refs, unsupported fields, unsupported point-attribute keys, or non-object metadata suppress that point-cloud preview object before stats or primitives are emitted. The QA runtime status ignores loaded reference data when the project pointer is invalid, the loaded manifest asset id does not match the project asset id, or the loaded manifest source format is not a supported canonical token, and uses the same safe wrapper-id check before counting a selected preview chunk as loaded. QA status, Project Files, and source-search runtime summaries apply the same loaded-asset id/source-format alignment, reject path-like loaded manifest names as row labels, and count only canonical layer/object map entries and manifest chunk ids whose safe ids align with their keys or declared ids instead of using raw container sizes.

## Pipeline

```text
DXF / DWG / STEP / IFC / E57
        |
        v
format-specific translator
        |
        v
bobercad-reference-geometry JSON
        |
        v
viewer reference layer
```

The app owns the canonical JSON contract in `bobercad/app/schemas/reference-geometry.schema.json`. Format-specific translators are adapters. If one source format fails, fix that translator or its mapping into the canonical schema rather than changing the BIM project model. Final private completion evidence cross-checks promoted-import artifacts instead of treating them as unrelated files: disposable project `referenceGeometry.assets` ids must be backed by promoted reference manifest `asset.id` values, promoted manifest and point-cloud sidecar `$schema` references must be non-empty, promoted manifest coordinate systems must be finite and non-degenerate, promoted manifest `asset.source` provenance must stay schema-closed with canonical source format/requested-format/file-extension aliases, path-free `fileName` values, strict RFC3339 `modifiedTime` values, and safe translator tokens, promoted manifest `layer`, `object`, `chunk`, and `diagnostics[]` envelopes must stay schema-closed with canonical display controls, kind-specific geometry payload fields, and diagnostic object references that point at existing objects, promoted manifest and sidecar bounds must be finite ordered bounds and match their object/asset payloads, line/mesh topology indices must stay inside their vertex payloads and be non-degenerate, promoted inline point-cloud `pointAttributes` values must be canonical with nonzero normal vectors, promoted manifest `chunks[].path` values must remain schema-safe point-cloud sidecar paths, every promoted manifest `chunks[]` entry must be owned by the matching `point-cloud` object `chunkIds` and have matching point-cloud chunk sidecar evidence, every sidecar `id`/`objectId` pair must be referenced by promoted manifest `chunks[]`, sidecar `bounds` must match the actual point payload, sidecar `pointAttributes` values must be canonical with nonzero normal vectors, and sidecar `pointCount`/`bounds` must match its promoted manifest chunk so duplicate sidecar refs cannot hide stale chunk evidence, and project pointers remain path-only without embedded canonical geometry payloads.

Repository contracts enforce this boundary: modules under `bobercad/app` must not import the translator, importer, adapter wrappers, or adapter contract helpers from `tools/reference-geometry`. The app consumes only project pointers plus canonical reference manifests and point-cloud chunk JSON. UI workflow metadata is also closed before it enters panel/session state: source-format tokens, adapter ids, execution/workflow modes, translation modes, adapter output modes, and next-action routing tokens must match the app-published whitelists, with unknown or path-like values dropped instead of driving workflow navigation. The next-action whitelist is regression-checked against the translator/importer producer files so valid producer tokens such as adapter-config setup, compatible-adapter selection, audit overlay use, and importer failure repair are not accidentally filtered out while execution modes remain separate. The browser runtime treats the metadata records it uses as closed canonical records: manifest, asset, `asset.source`, layer, object, diagnostic, manifest chunk, and point-cloud chunk sidecar entries reject unknown top-level fields before rendering or loading point-cloud chunks; nested canonical `bounds` and `asset.coordinateSystem` records also reject unknown fields, and optional object and sidecar `metadata` must remain objects.

## Translator CLI

The first translator entrypoint is:

```powershell
node .\tools\reference-geometry\translate_reference_geometry.mjs --input .\path\source.dxf --output .\bobercad\data\references\source.reference.json
```

External formats use the same entrypoint with a local adapter config:

```powershell
node .\tools\reference-geometry\translate_reference_geometry.mjs --input .\path\source.step --format step --adapter-config .\tools\reference-geometry\reference_geometry_adapters.local.json --output .\bobercad\data\references\source.reference.json
```

The CLI writes a `bobercad-reference-geometry` JSON file and sets its local `$schema` path relative to the output file. The output should be referenced from project JSON through `referenceGeometry.assets`, not copied into `model` or `objectIndex`. Canonical reference manifests and point-cloud chunk sidecars must use the exact schema versions supported by this workspace; future or unknown `schemaVersion` values are rejected during translator validation and project reference audits. Asset, layer, object, and chunk ids use a constrained source-independent identifier shape: start with a letter or digit, then use only letters, digits, `_`, or `-`; reserved JavaScript object keys are not valid canonical ids. Explicit `--asset-id` values are validated against that shape and rejected before translator/request/import writes instead of being silently sanitized; only ids inferred from source file names are sanitized. Explicit `--name` values are trimmed and must remain non-empty, so a whitespace-only display name fails before translator/request/import writes instead of silently falling back to the file name or asset id. CLI options that take values must carry an explicit non-empty value, either as the next argument or after `=`; a following `--flag` or an empty `--option=` is treated as a missing value and rejected before any translator, adapter request, project, or manifest write. Unknown CLI arguments are also rejected before writes, so typos in automation cannot silently fall back to a built-in translator or default project reference placement. Required asset/layer display names and optional object display names must be non-empty when present, so UI and audit summaries are not forced to invent labels for adapter output.

Project reference asset ids, fields, transforms, display metadata, and paths are schema-guarded to the viewer/import boundary shape. The viewer runtime also rejects unknown project pointer fields, unsafe pointer paths, unknown project transform fields, and unsupported reference display override fields before manifest fetch, so manually edited project JSON cannot smuggle translated geometry payloads or local adapter metadata through `referenceGeometry.assets`. Domain validation also rejects reference asset ids that appear in `objectIndex`, standard `model` collections, top-level `model` fields, or `model.addonData`, so extensible model metadata cannot become a hidden canonical-manifest store. Importer discovery reads the asset id pattern, reserved object-key exclusions, required/optional asset fields, display schema fields, transform fields, and path pattern from `project.schema.json` and exposes them through `referenceProjectPointerContract.assetIdPattern`, `assetIdPatternSource`, `assetIdReservedKeys`, `assetIdReservedKeysSource`, `requiredAssetFields`, `requiredAssetFieldsSource`, `optionalAssetFields`, `optionalAssetFieldsSource`, `displaySchemaFields`, `displaySchemaFieldsSource`, `displaySchemaAllowsAdditionalProperties`, `displayOverrideFields`, `displayOverrideFieldsOutsideProjectDisplaySchema`, `transformFields`, `transformFieldsSource`, transform default policy fields, and `pathPolicy`. The same contract lists forbidden project-pointer geometry payload fields such as canonical schema, asset, layer, object, chunk, point, face, attribute, bounds, diagnostics, metadata, and loaded-chunk fields, plus forbidden import-runtime fields such as adapter request, stage, scratch, chunk, log, source, output, and target manifest paths. Project reference paths must use a direct `../references/<manifest>.json` pointer with a safe filename; URLs, absolute paths, backslashes, query or fragment paths, empty path segments, nested manifest directories, non-JSON manifest filenames, uppercase extension variants, traversal segments, percent-encoded filename characters, encoded slash/backslash/traversal, malformed percent escapes, control characters, trailing whitespace, and paths outside `../references/` are rejected before domain validation, reference audits, or runtime loading can inspect the target. `pathPolicy` includes `schemaGuarded`, `schemaPattern`, `schemaPatternSource`, direct-manifest/JSON-extension requirements, and the individual reject flags, so UI and CI can consume the project pointer boundary without opening `project.schema.json`.

The same project pointer discovery contract reads canonical manifest identity from `reference-geometry.schema.json` and exposes it in `manifestAlignment.manifestSchema`, `manifestSchemaSource`, `manifestSchemaVersion`, and `manifestSchemaVersionSource`. It also exposes the canonical manifest id pattern and reserved keys plus booleans proving the project asset id shape matches the canonical manifest id shape. This keeps the project-side attachment contract aligned with the canonical JSON schema without hardcoding a second manifest schema/version/id contract in importer discovery.

Importer `--check-references` treats malformed project JSON as an audit input failure, not as an unstructured CLI crash. It still returns the normal machine-readable audit envelope and reduces project parse/schema-check failures to path-free class messages, so private project paths and raw parser text do not enter review artifacts while the repair remains clearly scoped to the project pointer/audit input. Malformed canonical reference manifests and canonical manifest schema-check failures use the same audit boundary: asset summaries report a `read-error` with a path-free manifest parse or schema-check class, and top-level audit errors point at the project reference asset path field rather than echoing raw parser text, missing schema file names, or local manifest paths. Unsupported canonical manifest `schema` or `schemaVersion` values keep the audit status as `unsupported-schema`, but top-level errors still use path-free project-asset messages instead of local manifest paths or raw schema-validation text. Canonical object/layer/chunk ids, object layer refs, diagnostic object refs, diagnostic codes, diagnostic messages, and chunk-entry ids included in bounded public audit summaries are filtered through the same schema-backed safe-id and diagnostic policies before they are copied to summary entries or count keys.

When project schema validation reports a failing `referenceGeometry.assets` map key, the audit JSONPath replaces unsafe key text with `<invalid-reference-asset-id>`. Invalid project asset keys are not copied into `assets`, `referenceAssetEntries`, `referenceNeedsAttentionEntries`, or summary-only output, because the schema error itself is the repair signal and the raw key may be a pasted local path.

Project pointer metadata copied into audit summaries is filtered before publication. Pointer `path` values must be relative strings without absolute roots, drive or URI prefixes, backslashes, query/hash suffixes, control characters, or encoded slash/backslash separators before they are echoed or statted, display overrides are reduced to valid `color`, `edgeColor`, `opacity`, and `pointSize` values, and transforms are reduced to finite vec3 axes/origin plus positive scale. Translator and importer discovery schema identity rows are tested against the local reference geometry, point-cloud chunk, adapter request, and adapter config schema files. The translator, importer, adapter request validator, and production adapters also derive supported schema names and versions from those local schema files instead of maintaining separate literals. Valid adapter-request summaries and written request payloads are checked against the same local schema versions. Production adapters that emit canonical reference manifests or point-cloud chunk sidecars must use the schema versions supplied by the validated adapter request. A schema identity change must therefore update the discovery output intentionally instead of passing through a stale literal in the smoke tests.

The reference manifest owns the source asset coordinate frame in `asset.coordinateSystem` and source length units in `asset.units`. The viewer converts canonical asset units to the project length unit, applies the manifest coordinate frame, then applies `referenceGeometry.assets.<assetId>.transform`. Translator fixes remain local to the canonical JSON while project placement stays pointer-only. Translator validation rejects non-finite, zero-length, or degenerate source coordinate axes before a canonical manifest is promoted.

Built-in translators detect supported source length units when the source declares them: DXF `$INSUNITS`, STEP `LENGTH_UNIT` with `SI_UNIT` or `CONVERSION_BASED_UNIT`, and IFC `IFCSIUNIT` or `IFCCONVERSIONBASEDUNIT`. Conversion-based STEP and IFC units can be recognized by a supported unit label or by a supported metre conversion factor. The canonical unit set is intentionally small: `mm`, `m`, `in`, and `ft`. Unsupported declared units are reported as translator diagnostics instead of guessed. Pass `--units` to override detection for a specific import; the override is validated before translation or adapter request generation and fails with `reference-units-invalid` unless it normalizes to `mm`, `m`, `in`, or `ft`.

The built-in DXF translator accepts ASCII group-code/value DXF streams with `SECTION` records. Binary DXF headers or malformed text that lacks the ASCII DXF structure fail before any canonical manifest is written; convert those inputs to ASCII DXF or route them through an external adapter. DXF layer names that are already safe canonical ids are preserved as layer ids; unsafe source layer names are sanitized into stable layer ids while the original layer name remains in `layers.<id>.name`.
The built-in STEP and IFC translators require at least one Part 21 entity record (`#id = TYPE(...)`); malformed files without entity records fail before output promotion and should be repaired or handled by an external adapter.
The built-in STEP and IFC translators also resolve `PRESENTATION_LAYER_ASSIGNMENT` / `IFCPRESENTATIONLAYERASSIGNMENT` for mesh, point, and curve linework when the assignment targets a representation or contained geometry item. The layer name is sanitized into a canonical `step_layer_<name>` or `ifc_layer_<name>` layer id before output, so the app runtime receives ordinary source-independent layer/object records instead of interpreting STEP or IFC layer semantics.

Smoke coverage includes STEP conversion-based `INCH` detection, IFC conversion-based `FOOT` detection, and factor-based imperial fallback detection for non-canonical conversion unit labels, so imperial references keep canonical units in `asset.units` without source-specific app runtime branches.

Mapped STEP and IFC smoke coverage includes non-uniform X/Y/Z target transforms for meshes and linework, so instance scaling remains an isolated translator concern and canonical geometry arrives already expanded into one source-independent JSON shape.

All translator outputs are staged and validated before the target manifest is replaced. Built-in translators, canonical JSON passthrough, and external adapters use the same final promotion path, and final manifest/chunk sidecar writes use same-directory temp JSON files that are schema/domain validated before rename. Final promotion keeps backups for an existing target manifest and existing chunk sidecars, rolls back chunk sidecars if manifest replacement fails, and restores the prior manifest if an error occurs after replacement. Backup files are removed only after a successful restore or successful promotion; if restore itself fails, the backup remains beside the target for manual recovery. A failed validation should leave an existing reference asset manifest untouched, and successful promotion should not leave temp promotion files beside the reference asset.

Project reference transforms are placement metadata, not source geometry. Missing axes default to the project basis, but any supplied vector tuple must contain exactly three numbers, any supplied axis must be finite and non-zero, and the final `axisX`/`axisY`/`axisZ` basis must be non-degenerate. `referenceProjectPointerContract` exposes this as importer/runtime policy, not JSON Schema defaults: `transformDefaultsAreSchemaDefaults` is false, missing fields use the project basis, and the resulting basis still must be non-degenerate. The importer rejects invalid transform, display, and boolean overrides before translation or promotion, and schema/domain validation catches manual project edits with invalid reference transform metadata. JSON failures use stable codes for automation: `cli-boolean-invalid` for boolean flags, `reference-vector-invalid` for malformed vectors, `reference-number-invalid` for non-finite numeric values, `reference-positive-number-invalid` for non-positive scale or point size, `reference-opacity-invalid` for opacity outside `[0, 1]`, `reference-color-invalid` for invalid colors, and `reference-transform-invalid` for degenerate transform bases.

Use `--replace-existing` for translator iteration: it refreshes the existing canonical manifest at the existing project pointer path while preserving the BIM `model`, `objectIndex`, and existing pointer placement/style metadata unless explicit overrides are supplied.

Use the lower-level translator when debugging a source-format adapter. Use the importer when the goal is to attach the translated reference asset to a project.

When `--format` is omitted, the translator and importer infer the source format from the file extension. Alias extensions normalize to the same canonical adapter request path: `stp`, `p21`, and `stpnc` route to `step`; `ifcxml` and `ifczip` route to canonical `ifc` adapter requests but require an external adapter because the built-in IFC path only parses Part 21 text; `e57pointcloud` and `e57pc` route to `e57`. Explicit `--format` values must be lowercase-style source format tokens; values with spaces, leading dots, path separators, or MIME-like slashes fail with `reference-format-invalid` before adapter requests, adapter preflight selection, project files, or reference manifests are written. The same validation applies to direct API calls that pass an explicit format into translator/importer helpers. Valid but unregistered explicit or inferred source format tokens fail with `reference-format-unsupported` before adapter requests, project files, or reference manifests are written. Adapter requests receive canonical `format` values (`dxf`, `dwg`, `step`, `ifc`, or `e57`) plus `requestedFormat`, which preserves the user-supplied or extension-inferred token such as `p21`, `ifczip`, or `e57pointcloud`. `requestedFormat` and source extension fields are lowercase token fields, not raw filenames or MIME strings; schema validation rejects spaces, leading dots, and path-like separators before adapter requests or canonical manifests are accepted.

Use the importer in check-only mode to audit the reference assets already attached to a project without translating a new source file or rewriting the project. `--check-references` accepts `--project`, optional `--asset-id`, optional `--references-dir`, optional `--summary-only`, and `--json`; it rejects import, adapter, display, and transform options with `cli-option-combination-invalid`, so a mixed command cannot silently audit when automation meant to import. `--summary-only` is valid only with `--check-references`; using it with import, plan-only, dry-run, or adapter-request workflows fails before project or manifest writes.

Add `--asset-id <id>` to audit only one attached reference asset. This is useful after a single import or replace-existing iteration. Add `--summary-only` when an import panel, poller, or CI guard only needs the bounded top-level index, needs-attention index, aggregate totals, bounded error summary, audit fingerprint, `referenceAuditDecision`, and errors; this keeps the selected `assets` object out of stdout while preserving enough data to decide whether a later full audit is needed. Summary-only output is local-path-free: it omits top-level `projectPath`/`referencesDir`, omits `referenceAuditDecision.projectPath`, and removes `resolvedPath` from bounded asset and needs-attention entries while preserving schema-constrained project pointer `path` values for repair. The check validates that each selected `referenceGeometry.assets` entry stays pointer-only, resolves under the active references directory, points to an existing canonical manifest, has a matching manifest `asset.id`, and has valid point-cloud chunk sidecars. The active references directory is `bobercad/data/references` unless `--references-dir <dir>` is supplied for a custom import/check workflow. The JSON summary reports `projectFileName`, `projectFileSizeBytes`, `projectFileModifiedTime`, and `projectStatFingerprint` for the audited project file snapshot, `referenceAuditContractVersion` for the check-output contract, `referenceAuditLimits` for bounded list thresholds, whether each pointer resolves inside that references directory, per-asset `referenceAuditStatus` / `referenceReady` values, per-asset `referenceAuditSeverity` (`ok`, `warning`, or `error`) and numeric `referenceAuditStatusRank` for stable UI sorting, top-level `referenceAuditStatusDefinitions` for rank/severity discovery without hardcoding status metadata, bounded per-asset audit error entries, top-level `referenceReadyCount`, `referenceNeedsAttentionCount`, `referenceAuditStatusCounts`, and `referenceAuditSeverityCounts`, plus top-level `referenceAuditErrorCount`, bounded `referenceAuditErrorEntries`, and `referenceAuditErrorOmittedCount` for triage without scanning the full `errors` array. It also reports `referenceAuditDecision`, a compact routing decision derived from those audit counts: it reports whether the audit passed, whether reference overlays are render-ready, blocking status tokens, the highest-priority failing asset/status/severity, a likely fix area (`project-pointer`, `canonical-reference`, `mixed`, or `none`), and stable next-action tokens such as `load-reference-overlays`, `review-reference-audit`, `use-reference-overlays`, `fix-project-reference-pointer`, or `fix-canonical-reference-output`. It also reports bounded top-level `referenceAssetEntries` with asset id, path, ready/status/severity/rank, visibility/snap policy, display override metadata, transform origin/axes/scale, source format/adapter, manifest/artifact fingerprints, canonical counts, missing chunk count, diagnostic count, and audit error count, plus `referenceAssetEntryOmittedCount` when the selected set is larger than the bounded list. Non-ready reference assets are also exposed separately as bounded `referenceNeedsAttentionEntries` with `referenceNeedsAttentionEntryOmittedCount`, carrying path, status/severity/rank, read/schema identity, missing chunk count, and bounded per-asset audit errors so UI and automation can jump straight to broken references even when the full selected set is large. The needs-attention list is sorted by descending `referenceAuditStatusRank` and then ascending `assetId`, so the bounded result keeps the highest-priority failures first. It also reports a top-level `referenceAggregate` object for the selected assets, including ready/needs-attention counts, canonical manifest counts, object/layer/chunk totals, primitive totals, point-cloud and chunk file totals, diagnostic totals, status/severity counts, source format counts, source adapter counts, and object kind counts. The top-level `referenceAuditFingerprint` is a cheap `sha256:<hex>` token over the audit contract version, audit limits, selected asset paths, pointer visibility/snap/display/transform metadata, audit statuses, canonical manifest/artifact fingerprints, aggregate totals, and bounded top-level error entries/counts; it intentionally excludes local `resolvedPath` values so UI and automation can compare audit state across worktrees or temporary directories without diffing every asset summary. Missing-manifest summary-only audits with identical project pointer metadata must produce the same fingerprint even when the project lives under different local workspace roots. `referenceAuditDecision` is intentionally derived after that fingerprint so callers can cache audit state while still using the decision for UI routing. Status values are stable machine tokens such as `ready`, `missing-asset`, `missing-path`, `outside-references-dir`, `missing-manifest`, `unsupported-schema`, `asset-id-mismatch`, `missing-chunks`, `read-error`, and `invalid-reference`, so import UI and adapter automation can decide whether a translator iteration is render-ready or needs another canonical JSON/chunk fix without parsing human-readable validation errors. Manifest parsing and canonical summaries are skipped for existing files outside that directory, so a manually edited pointer cannot make the audit path read and summarize arbitrary workspace JSON. Contained files are summarized as canonical reference geometry only when they use the supported `bobercad-reference-geometry` schema/version; other contained JSON files may report basic schema metadata but do not expose source, bounds, primitive counts, chunk summaries, or diagnostic summaries as if they were reference manifests. Point-cloud sidecar file metadata is collected only from canonical forward-slash relative chunk paths without absolute roots, Windows drive prefixes, backslashes, query/fragment suffixes, plain `..` traversal, or encoded slash/backslash traversal. Missing or skipped sidecars are reported both as `referenceChunkFileMissingCount` and as a bounded `referenceChunkFileMissingEntries` list with `chunkId`, manifest `path`, and a reason such as `missing-file` or `unsafe-or-invalid-path`, so adapter automation can identify which E57-style chunk needs repair without statting unsafe paths. For valid contained references, the JSON summary includes manifest id, project reference visibility/snap policy/display/transform pointer metadata, canonical reference schema and schema version, canonical reference manifest file size/modified time/content fingerprint, point-cloud chunk sidecar file count/total size/latest modified time/missing count/stat fingerprint, bounded present `referenceChunkFileEntries`, and bounded missing-entry details, complete `referenceArtifactFingerprint` for manifest plus chunk sidecars when no chunk is missing, total manifest chunk point count, total line segment count, total mesh face count, total point-cloud point count across inline and chunked storage, bounded `referenceObjectIds`, `referenceLayerIds`, `referenceChunkIds`, bounded `referenceObjectEntries` with object kind/layer/bounds/primitive counts, bounded `referenceLayerEntries` with layer display metadata and object counts, and bounded `diagnosticEntries` with omitted counts, canonical reference units, asset bounds, source coordinate system, source format, source file name, source file extension, requested source format token, source file size, source file modified time, source stat fingerprint, source checksum, source translator, selected external adapter key when present, diagnostic severity/code counts, prefixed reference object/layer/chunk counts, and prefixed reference object kind counts so automation can inspect attached references without loading the viewer.

`missing-manifest` is a project pointer or promotion-state failure, not evidence that a source adapter produced invalid canonical JSON. It routes through `referenceAuditDecision.likelyFixArea: "project-pointer"` and `recommendedNextAction: "fix-project-reference-pointer"` and intentionally omits canonical manifest metadata because there is no manifest to inspect.

A requested `--asset-id` that does not exist is also a project-pointer failure. Its public audit error is limited to `referenceGeometry.assets.<assetId> does not exist`, and summary-only audits with the same missing asset selection must keep the same `referenceAuditFingerprint` across local workspace roots.

`outside-references-dir` is reported when a project reference pointer resolves outside the active references directory. It routes through project-pointer repair and intentionally skips canonical manifest reads, even if the target file exists, because the project pointer boundary failed before any reference manifest can be trusted.

`missing-path` is reported when a project reference asset exists but has no usable `path`. It routes through project-pointer repair and intentionally skips canonical manifest reads because there is no safe manifest location to inspect.

`missing-asset` is reported only for targeted `--asset-id` audits where that asset id is absent from `project.referenceGeometry.assets`. It also routes through `project-pointer` repair, with the requested asset id repeated in `referenceAuditDecision.highestPriorityAssetId`, so UI can clear the selected target or ask the user to import/choose an existing reference asset.

`read-error` is reported for contained reference manifest files that exist but cannot be parsed as JSON. It routes through canonical-reference repair because the project pointer is valid enough to locate the file, but the translated manifest itself must be regenerated or fixed before the viewer can read it.

`unsupported-schema` is reported for contained JSON files that can be read but are not supported `bobercad-reference-geometry` manifests. It routes through canonical-reference repair because the pointer reached a safe file, but the file is not valid translator output for reference overlays.

`missing-chunks` is reported when a canonical reference manifest depends on point-cloud sidecars that are missing or unsafe to read. It routes through canonical-reference repair because E57-style chunk sidecars are part of the translator or adapter output contract, not project pointer metadata or a viewer fallback.

Stale or unverifiable canonical `asset.bounds` are an audit failure, not a viewer fallback. `--check-references` reports them as `invalid-reference` with `likelyFixArea: "canonical-reference"` and `recommendedNextAction: "fix-canonical-reference-output"`, keeping the repair loop inside the translator or adapter output.

Project asset keys must match the attached manifest `asset.id`. When they do not, `--check-references` reports `asset-id-mismatch` with `likelyFixArea: "project-pointer"` and `recommendedNextAction: "fix-project-reference-pointer"`, so automation can distinguish a bad pointer from a translator output defect.

When one audit includes both project-pointer statuses and canonical-reference statuses, `referenceAuditDecision.likelyFixArea` is `mixed` and `recommendedNextAction` is `fix-reference-audit-findings`. This keeps UI and CI from suggesting a single repair loop when both the project pointer and translated canonical output need attention. The same decision, blocking statuses, needs-attention ordering, bounded errors, and audit fingerprint must be preserved in `--summary-only` output so polling surfaces can route mixed failures without loading full per-asset summaries.

## External Adapter Contract

External adapters are configured locally with `bobercad-reference-geometry-adapters` JSON. The checked-in `tools/reference-geometry/reference_geometry_adapters.example.json` shows the contract; machine-specific local copies should point at real adapter executables. This workspace accepts only adapter config `schemaVersion: "0.1.0"`; future or unknown adapter config versions fail schema validation before discovery or preflight, so wrapper contracts must be migrated intentionally. Adapter object keys are stable adapter ids: they must start with a letter or digit, use only letters, digits, `_`, or `-`, and avoid reserved JavaScript object keys; path-like names, spaces, and slash separators are rejected before discovery or preflight. Adapter `formats`, `requiredFiles`, `requiredDirectories`, `requiredCommands`, and `requiredEnv` arrays are set-like declarations and must not contain duplicates, so discovery/preflight output does not mask repeated local config entries. The example declares the same common aliases the translator normalizes, including DXF/DWG through the same bridge slot, STEP `stp`/`p21`/`stpnc`, IFC `ifcxml`/`ifczip`, and E57 `e57pointcloud`/`e57pc`, so copied local configs accept the same source extensions by default. The translator validates the adapter config against its local `$schema` before selecting or launching an adapter, and a named adapter must declare support for the requested source format, so invalid local config or mismatched adapter selection fails before any external process can write output. Adapter `outputMode` defaults to `file`, where the adapter writes canonical `bobercad-reference-geometry` JSON to `{output}`. Set `outputMode` to `stdout` only when the adapter writes the complete canonical manifest to process stdout; the translator captures that stdout into the staged `{output}` file before normal manifest and sidecar validation, while the full stdout stream remains available in `{adapterStdoutPath}` when a stage is kept. Adapter `streamMaxBufferBytes` optionally raises or lowers the adapter process stdout/stderr capture buffer from the default 67108864 bytes; file output remains preferred for large references, and a run that exceeds the configured buffer fails as `adapter-stream-buffer-exceeded` before promotion.

A direct chunking adapter should write sidecar files under `chunkDir` and set manifest `chunks[].path` to `${chunkPathPrefix}<file>.json`, for example `chunks/e57_scan_0001.json`. Inline point clouds larger than the configured chunk threshold are split into chunk sidecars during promotion, and the final manifest keeps only `chunkIds` for that object.

The E57 XYZ bridge normalizes `D`/`d` scientific exponent point-text numbers like `E` exponents before parsing coordinates, colors, intensities, classifications, normals, and spherical angles.

The E57 XYZ bridge also normalizes short and E57-style color channel labels such as `color.r`, `color.g`, `color.b`, `colour.r`, `colour.g`, `colour.b`, `cartesianRed`, `cartesianGreen`, and `cartesianBlue` to canonical `r`, `g`, and `b` point attributes before writing point-cloud chunks.

The E57 XYZ bridge also normalizes E57-style normal-vector labels such as `cartesianNormalX`, `cartesianNormalY`, and `cartesianNormalZ` to canonical `nx`, `ny`, and `nz` chunk attributes. The same alias map is used by adapter preflight and runtime parsing, so configured point-text columns fail or pass before launch the same way emitted headers are parsed.

The E57 XYZ bridge also normalizes common scalar/classification aliases such as `cartesianIntensity`, `intensityValue`, `intensityRaw`, `reflectance`, `reflectivity`, `amplitude`, `classId`, `classCode`, and `classificationValue` to canonical `intensity` and `classification` point attributes before chunk sidecars are written.

The E57 XYZ bridge strips repeated trailing header suffixes such as `X Coordinate [m] (float)` before column alias matching, so exporter unit/type annotations remain adapter-local metadata.

The E57 XYZ bridge also accepts single-column packed color exports named `rgb`, `color`, `colour`, `rgba`, or related hex aliases. Plain `rgb` accepts decimal packed integers and PCD/PCL float32-bit text values, and marked hex aliases such as `rgbHex`, `colorHex`, and `rgbaHex` preserve hex parsing even when the bare six/eight-character token contains only digits. Decimal/hex/float packed RGB values become canonical RGB triplets, and packed `rgba` values use `RRGGBBAA` order while alpha is ignored because reference point-cloud chunks store colors as RGB only.

For CAD/OBJ bridge vertex colors, `BOBERCAD_CAD_OBJ_VERTEX_COLOR_LAYOUT` accepts `auto`, `weighted-rgb`, or `rgba`. Use `rgba` for tessellators that write OBJ vertex colors as `v x y z r g b a`; the bridge ignores alpha and writes canonical RGB point attributes. The default `auto` preserves the existing weighted-RGB interpretation for `v x y z w r g b`, and preflight rejects unknown layout values before launching the local tessellator.

The CAD/OBJ bridge accepts decimal-comma numeric tokens and `D`/`d` scientific exponents in staged OBJ vertex coordinates, vertex colors, homogeneous weights, and MTL `Kd`/`d`/`Tr` material values, converting them before canonical mesh, line-set, point-cloud, and display metadata are written.

The CAD/OBJ bridge normalizes staged OBJ face records that close a polygon by repeating the first vertex at the end before writing canonical mesh faces. It rejects face records that still resolve to fewer than three distinct vertex references, face records with consecutive duplicate vertex references, face records with repeated non-closing vertex references, and line records with consecutive duplicate vertex references before writing canonical mesh or line-set objects, so degenerate tessellator output stays inside the adapter boundary.

The built-in DXF translator also normalizes `D`/`d` scientific exponent group-value numbers before emitting linework, point, and mesh geometry, so CAD exports using Fortran-style numeric notation stay inside the translator boundary.

The built-in DXF translator ignores ASCII DXF group-code `999` comment pairs before entity parsing, so source comments cannot become canonical entity data or viewer-facing diagnostics.

The built-in STEP Part 21 and IFC Part 21 translators normalize `D`/`d` scientific exponent numeric tokens before resolving point tuples, scalar geometry parameters, transforms, and style ratios into canonical objects.

The built-in STEP Part 21 and IFC Part 21 translators strip block comments outside quoted strings before entity scanning, so commented-out `#id = TYPE(...)` records cannot leak into canonical reference objects.

The built-in STEP Part 21 and IFC Part 21 reference resolver ignores `#id`-looking text inside quoted strings when resolving entity relationships, so labels or product names cannot accidentally redirect placements, representation items, or style links.

DXF classic `POLYLINE` polygon mesh face vertices use the header extrusion normal for OCS-to-WCS placement before canonical mesh output, matching the OCS handling already used for classic polyline linework.

The E57 XYZ bridge also normalizes survey-style ENU point-text columns such as `Easting`, `Northing`, `Elevation`, `East`, `North`, `Height`, and `Altitude` to canonical Cartesian `x`, `y`, and `z` before point-cloud chunk sidecars are written. It accepts coordinate-label variants in either order, including `coordinateX`, `coordX`, `XCoord`, `XPos`, `PosX`, `PositionX`, `cartesianXCoordinate`, and quoted CSV headers such as `X Coordinate`, `Position X`, or `Cartesian X Coordinate`. Comment-prefixed E57 headers may be bare column lists or labeled lists such as `# Columns: X,Y,Z,...`; they may also carry leading non-geometry metadata columns such as `ScanId`, `Row`, `Column`, `GPSTime`, `PointId`, `ReturnNumber`, `NumberOfReturns`, and `ScanAngle` before the coordinate columns. Those metadata values stay adapter-local and are ignored when writing canonical point-cloud chunks. Ambiguous `Elevation` / `Elev` headers resolve contextually inside the adapter and adapter preflight: with `Easting` and `Northing` they become Cartesian `z`, while with `Range` and `Azimuth` they become `sphericalElevation`.

## Canonical Shapes

The first canonical surface supports:

- `line-set` for DXF/DWG linework and wire overlays
- `mesh` for tessellated STEP/IFC solids or surfaces
- `point-cloud` for small inline scan previews and chunked E57-style scan data

Reference objects must contain real geometry payloads: `line-set.lineSegments`, `mesh.faces`, inline `point-cloud.points`, and chunked `point-cloud.chunkIds` must not be empty. Geometry payload fields are kind-specific: `line-set` may carry only `vertices` and `lineSegments`, `mesh` may carry only `vertices` and `faces`, and `point-cloud` may carry only `points`, `pointAttributes`, or `chunkIds`. These kind-specific payload, non-empty payload, unique `point-cloud.chunkIds`, and minimum `line-set`/`mesh` vertex-count rules are schema-level checks so invalid adapter output is rejected before domain validation. Line segments must reference two distinct vertices, and mesh faces must reference at least three distinct vertices. Empty or degenerate source entities should be dropped by the translator or reported as diagnostics, not emitted as canonical objects.

Layer map keys are part of the canonical contract and must match each layer `id`. The translator validates this before promotion so adapter-local naming mistakes do not leak into viewer styling or object layer references.

Optional `bounds` metadata on assets, objects, and chunks must use finite `[x, y, z]` `min`/`max` vectors with `min <= max` on every axis. Final line-set and mesh object bounds must match their vertex payloads, and asset bounds must match the complete union of canonical object payload bounds; if any referenced object payload lacks verifiable bounds, the asset bounds are invalid. Final inline point-cloud object bounds must match the real inline point payload. Bounds are used as canonical reference metadata and diagnostics; malformed adapter bounds should be fixed in the translator output rather than normalized by the viewer.

Diagnostic entries must include safe machine-readable `code` tokens and bounded human-readable `message` values. Messages may mention source-format entity handles, entity types, counts, and supported semantic context such as `boolean/clipping`, but they must not carry local paths, URI prefixes, traversal, encoded path separators, or file-like adapter log/staging paths. They may include `objectId` only when it points to a canonical reference object in the same manifest. Source-format entity handles should stay in the diagnostic message or adapter-specific metadata, not in `diagnostics[].objectId`.

Large point clouds should use `chunks` rather than storing millions of points inline. The translator can enforce this for canonical JSON or external adapter output with `--point-cloud-chunk-size`.

Each `point-cloud` object must use one storage mode: inline `points` for small previews or `chunkIds` for chunked sidecars. Do not emit both on the same object, and do not repeat a chunk id inside one `chunkIds` array. Schema validation enforces the exclusive storage mode before domain validation inspects chunk ownership, and direct scene construction applies the same storage-mode gate before preview primitives or preview-stat object entries are emitted. If an adapter starts with inline points and the payload is above the configured threshold, the translator moves those points into chunks, recalculates the point-cloud object bounds from the real point payload, and removes the inline payload from the final manifest. Small inline point-cloud payloads that stay inline must already have bounds matching their points before promotion. Chunked point-cloud object bounds must match the complete union of the referenced manifest chunk bounds, and every referenced manifest chunk must carry bounds when the point-cloud object declares bounds.

Point-cloud objects and chunk sidecars may include `pointAttributes` arrays for E57-style per-point data: `colors`, `intensities`, `classifications`, and `normals`. Object-level `pointAttributes` are valid only beside inline `points`; chunked point-cloud attributes must live in the corresponding sidecar files. Present attribute arrays must be non-empty and aligned 1:1 with the point array they live beside. `colors` values must be RGB triplets in the canonical 0-255 range, `intensities` must be finite numbers, `classifications` must be non-negative integers, and `normals` must be finite nonzero vec3 values; the browser loader enforces the same constraints before rendering sidecars or inline point clouds. Direct scene construction also filters point-cloud attributes per array before preview coloring: out-of-range RGB arrays are not clamped into display colors, and arrays whose lengths do not match the point payload are ignored, so invalid direct test/caller payloads fall back to aligned intensity or object style colors. When inline points are split into chunks, the translator moves matching `pointAttributes` into atomically written generated chunk sidecars, writes matching manifest and sidecar bounds for each generated chunk, and removes the large inline arrays from the manifest.

For externally generated chunk sidecars, `chunks[].path` is a canonical forward-slash relative path under the staged manifest directory, normally using the adapter request `chunkPathPrefix` value `chunks/`. The schema rejects absolute paths, Windows drive paths, backslashes, and `../` traversal, and the translator repeats path containment checks before promotion. When present, manifest chunk bounds must match the sidecar bounds, and sidecar bounds must match the actual point payload. If object or asset bounds depend on chunked point-cloud data, every referenced manifest chunk must carry bounds so the union is complete. Stale or partial E57 adapter bounds fail validation before promotion rather than being corrected by the viewer. Importer `--check-references` audit output keeps missing/invalid chunk paths manifest-relative in bounded repair entries, but reduces unsafe chunk paths, missing sidecar files, malformed sidecar JSON, sidecar schema validation/check failures, id/objectId/count/attribute mismatches, and stale sidecar/point-payload bounds to path-free class messages instead of echoing raw parser, schema-file, manifest-path, sidecar-path, or local directory details.

The viewer may use `pointAttributes.colors` or `pointAttributes.intensities` to color the read-only scan preview. These attributes remain reference overlay data only; they do not become project objects, fabrication data, or semantic BIM metadata.

The viewer renders reference overlays as bounded previews, controlled by `viewer-settings.json` at `render.referenceGeometry.pointPreviewLimit`, `render.referenceGeometry.pointPreviewChunkLimit`, `render.referenceGeometry.lineSegmentPreviewLimit`, and `render.referenceGeometry.meshFacePreviewLimit`. These budgets are applied before preview geometry is expanded into scene primitives. For point clouds, the runtime loads only the chunk sidecars needed for the configured point preview budget and stops selecting sidecars at `pointPreviewChunkLimit`, so an E57 adapter that emits many tiny chunks cannot force unbounded browser fetches. Large E57 scans and dense DXF/STEP/IFC references stay in canonical JSON/chunks for translator/debug workflows without forcing the app to draw, fetch, or transform every point, chunk sidecar, line segment, or mesh face. The built scene also exposes runtime-only `referenceGeometryPreviewStats` with the active limits, rendered/omitted point/segment/face totals, clipped object counts, and bounded per-object entries. Scene primitive metadata and preview-stat object entries are emitted only for safe reference asset/object ids, direct scene construction renders layered objects only when `object.layer` points to an existing matching safe layer id, and direct scene construction accepts only canonical `#RRGGBB` display colors plus opacity values in the `0..1` range before falling back to viewer defaults or the next valid display source, even when a test or future caller passes reference assets directly to the scene builder. The QA bridge exposes a defensive copy of the current scene stats through `window.__boberCadQa.referenceGeometryPreviewStats()` and the existing `bobercad:qa-request` DOM bridge. It also exposes pointer-only runtime load status through `window.__boberCadQa.referenceGeometryRuntimeStatus()`, including safe project asset ids, safe project pointer paths, loaded/not-loaded status, source format, object/layer/chunk counts, budget-selected preview chunk counts, `missingPreviewChunkCount`, `omittedPreviewChunkCount`, diagnostic code counts, and bounded sanitized load diagnostics (`stage`, `severity`, `code`, `message`, optional object/chunk id) without returning canonical object payloads, unsafe project reference pointers, runtime manifest URLs, or counting non-selected sidecars as preview-loaded. These status and preview stats are diagnostics for the viewer/UI/QA path only; they are not written back into project JSON or canonical reference manifests.

## Point-Cloud Chunks

Chunked point clouds use two JSON layers:

- the canonical reference manifest lists a `point-cloud` object with `chunkIds`
- each chunk path points to a `bobercad-reference-point-cloud-chunk` JSON sidecar containing points and optional aligned `pointAttributes` for that object

Chunk paths resolve relative to the canonical reference manifest. They should stay under `bobercad/data/references`, usually in `bobercad/data/references/chunks`. Manifest `chunks[].pointCount` is required, must be greater than zero, and must match the sidecar `pointCount`/point array length because the viewer uses manifest counts to decide which E57-style chunk sidecars are needed for the bounded preview.

Every manifest chunk must point to a `point-cloud` object, and every manifest chunk id must be listed in that owning object's `chunkIds`. Orphan chunks are treated as adapter output mistakes and rejected before promotion, because the viewer only loads sidecars reachable from `point-cloud.chunkIds`.

The viewer loads chunks defensively. A missing or invalid chunk removes only that chunk from the overlay and logs a warning; it must not prevent the project from loading.

## Final Proof Linkage

The saved completion-evidence source check and completion-evidence check both carry `evidenceSourcesFingerprint`, a path-free `sha256` fingerprint of the explicit evidence source manifest. The final proof bundle requires those values to match through `evidenceSourcesFingerprintAlignedOk`, so a 100 percent private proof cannot mix a source-check report and completion-evidence report from different evidence-source lists without reading private source paths or payloads again. Goal-completion audit reports this as `finalProofBundleEvidenceSourcesFingerprintAlignedOk` in `finalProofBundleAcceptanceFailures`, keeping the failure reason path-free and machine-readable.

Saved completion-evidence check reports repeat the manifest value policy as `summary.requiredValuePolicy`. The final proof bundle requires that value through `completionEvidenceRequiredValuePolicyOk`, so a hand-edited completion-evidence check with green gates but stale or mismatched path-free value policy cannot enter the final proof bundle.

The final proof bundle requires and republishes that value, and goal-completion audits require it through `finalProofBundleProofPlanFingerprintOk`, so a saved final-proof report cannot claim 100 percent completion with a stale proof-plan shape even if all older gates remain green. ## Runtime Rules

- Reference geometry is read-only.
- Reference geometry does not enter `objectIndex`.
- Reference geometry is not NC1 fabrication data.
- Bad or missing reference assets should not stop the project from rendering.
- Dense reference assets should render through bounded previews; fixing preview performance should happen in the reference layer or translator output, not by copying translated geometry into the project model.
- Snapping to reference geometry is opt-in through `referenceGeometry.assets.<assetId>.snapEnabled`. The snap provider uses the rendered read-only reference linework and mesh edges after canonical/project transforms, gives them lower priority than real project model snaps, and ignores point-cloud preview glyphs.
## SourceAdapter Exact-One Evidence

For sourceAdapter completion evidence, every DWG/E57 adapter-key, request-evidence fingerprint, adapter-config stat fingerprint, aggregate registry fingerprint, selected-adapter registry-entry fingerprint, and preflight fingerprint map is exact-one per family. Zero values or multiple values fail the final acceptance checker, completion-evidence verifier, final proof bundle verifier, and goal-completion audit, so extra same-family fingerprints cannot be treated as stronger proof.

Adapter-preflight proof is exact-one before those maps are built: each accepted DWG/E57 adapter-preflight evidence check must contain exactly one selected adapter key from the explicit `adapterPreflightDecision.selectedAdapterKeys` field, exactly one selected-adapter registry-entry fingerprint, and a safe `requested.adapter` value equal to that selected adapter key. The verifier also recomputes `adapterTargetFormatCoverageFingerprint` from the saved coverage JSON and requires the selected adapter key to appear in that family's target coverage entry, so a hand-edited preflight report cannot satisfy final proof with stale coverage fingerprints or aggregate target-format coverage that is not linked to the selected adapter. When the completion-evidence builder reads saved preflight evidence it also requires the top-level adapter config stat, aggregate registry, preflight, and target coverage fingerprints to match the same fields repeated in `summary`, because downstream sourceAdapter maps are built from summary fields. The verifier does not infer selected adapters from the registry when the decision field is missing, and the completion-evidence builder repeats that acceptance policy when reading saved preflight evidence, so manually widened, implicit, requested-adapter-free, stale-coverage, coverage-unlinked, or top-level/summary-mismatched preflight reports cannot satisfy source evidence.

Adapter-preflight evidence summaries also sanitize requested-field echoes. `summary.requestedFormat`, `summary.requestedFormatToken`, and `summary.requestedAdapter` may contain only known DWG/E57 family tokens, accepted requested-format aliases, or safe adapter keys; otherwise the saved evidence writes `null` while the matching gate fails. This keeps malformed or path-like requested values out of user-review proof JSON.

Diagnostic code summaries use the same privacy boundary: `blockingDiagnosticCodes`, `warningDiagnosticCodes`, and warning strings emit only safe lowercase machine tokens. Any `level: "error"` diagnostic in the saved preflight report still fails `preflightReportAcceptedOk`, even when its code is omitted from output for privacy.

Adapter keys in preflight and sourceAdapter proof maps also exclude reserved JavaScript object names: `__proto__`, `prototype`, and `constructor`. The adapter-preflight verifier rejects those names before emitting selected-adapter summaries, and the final-acceptance checker, completion builder, and downstream completion/final-proof/goal verifiers repeat the rule so a hand-written accepted proof JSON cannot reintroduce reserved keys.

Every sourceAdapter proof-chain contract that exposes `externalAdapterSourceAdapterKeys` also publishes `sourceAdapterKeyPolicy.safeAdapterKeyPattern` and `sourceAdapterKeyPolicy.reservedAdapterKeys`, so private proof runners can verify the reserved-key policy directly from `--list-contract` output.

The adapter-preflight evidence contract publishes the same rule as `familyPolicy.adapterKeyPolicy` because it validates `adapterPreflightDecision.selectedAdapterKeys` and `requested.adapter` before sourceAdapter proof maps exist.
